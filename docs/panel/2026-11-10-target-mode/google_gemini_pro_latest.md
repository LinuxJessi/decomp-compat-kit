# ~google/gemini-pro-latest

1. **False MATCH via self-resolving `FUN_` / `DAT_` names and `@addr` annotations (Verifier Bypass)**
   - **Location:** `tools/verify_decomp.py` (`OverlaySymbols.value`, `OverlaySymbols.known`, `parse_annotations`).
   - **Mechanism:** `OverlaySymbols` resolves any symbol matching `AUTO_NAME` (`^(?:FUN_|DAT_|LAB_|PTR_|[A-Za-z]*Ram)0*([0-9A-Fa-f]{6,8})$`) directly to the hex value in its identifier, and `parse_annotations` accepts arbitrary `/* @addr NAME 0xVA */` comments inside the C source being verified. A human or agent can force any relocation to resolve to the exact address encoded in the retail binary by naming an extern `FUN_<retail_va>` / `DAT_<retail_va>` or adding an `@addr` comment in the TU—even if that address belongs to a completely different symbol in `symbols.csv` or the middle of an instruction. `run_target` records the result as a clean "Tier A" match.
   - **Test:** In a target-mode TU, replace a valid call `foo()` (at `0x100000` in `symbols.csv`) with `extern void FUN_00100000(void); FUN_00100000();`, or add `/* @addr wrong_name 0x100000 */` and call `wrong_name()`. Run `verify_decomp.py --target ...` or `ledger.py check`: it reports a Tier-A `match` instead of a symbol mismatch or cheat.

2. **False MATCH on relocated pointers inside content-anchored data sections**
   - **Location:** `tools/verify_decomp.py` (`Object._anchored`, `Object._relocated_words`).
   - **Mechanism:** When verifying a section-relative data reference (e.g., a struct or array in `.data` or `.rodata`) by content, `_anchored` masks out every word in the span that has an entry in `.rel.<sec>` (`ours[wo - start: ...] = b"\0\0\0\0"; theirs[...] = b"\0\0\0\0"`) without evaluating or checking where those relocations point. A static struct containing `{ 0, &wrong_func }` or `{ &str_a, &str_b }` with completely wrong pointers will pass content verification as long as the non-pointer padding/integers match, and the referencing function will be marked Tier-A `match`. Worse, a data object consisting *entirely* of pointers (e.g. a function pointer table) has 100% of its bytes zeroed out, matching any aligned address in the retail binary.
   - **Test:** Create a TU with `static void (*tbl[])(void) = { wrong_fn1, wrong_fn2 };` referenced by a function. Compile and verify against a retail binary where the function loads a table of two pointers to `right_fn1, right_fn2`: `_anchored` masks all 8 bytes to zero, accepts the retail address, and reports `match`.

3. **False MATCH on short/zero-initialized data via `_site_va` circular anchoring and under-split `_object_span`**
   - **Location:** `tools/verify_decomp.py` (`Object._anchored`, `Object._object_span`, `Object._section_refs`).
   - **Mechanism:**
     1. When no `@rodata` / `@data` annotation is given, `_anchored` reads the target address `va` directly out of the retail binary's instruction at the relocation site (`_site_va`), then checks if `theirs` at `va` equals `ours`. If the C code defines a common constant (e.g., `0.0f` in `.lit4`, `""` in `.rodata`, or `static int x = 0;` in `.sdata`) and references the wrong variable in the retail function that happens to hold `0` in the retail binary image, it self-verifies.
     2. `_section_refs` only collects offsets from `.rel.text` HI16/GPREL16/LITERAL, non-text `R_MIPS_32`, and named symbols. It omits `R_MIPS_LO16` addends from shared-HI16 pairs (`_section_lo_shared`). If a function accesses two adjacent anonymous objects (e.g., two strings or floats) via a shared `%hi` and two `%lo` relocations, the second object's start offset is missing from `_section_refs()`. `_object_span` merges both objects into one span; or conversely, if the C code references the middle of an object, `_section_refs` splits the object in two at the interior addend, checking fewer bytes than the actual object size.
   - **Test:** Emit a function that loads two `.rodata` strings via a single `lui` and two `addiu` (`R_MIPS_HI16` at +0, `R_MIPS_LO16` at +0, `R_MIPS_LO16` at +8). Inspect `o._object_span(rodata_shndx, 0)`: it returns `(0, total_size)` instead of `(0, 8)`, and `starts` in `_anchored` has length 1 instead of 2, breaking `@rodata` index mapping.

4. **Forced-difference corruption on `%hi`/`%lo` content mismatch leaves `%hi` un-relocated or corrupts shared `%lo`**
   - **Location:** `tools/verify_decomp.py` (`Object._apply_hi_pair`, lines 452–457).
   - **Mechanism:** When `_anchored` fails with a `"content..."` mismatch inside `_apply_hi_pair`, it appends to `self.placeholders`, sets `self._pending_lo[noff] = 0`, and returns `None` without modifying the `R_MIPS_HI16` instruction at `off` (leaving the raw section addend in the `lui` immediate) and zeroes the paired `R_MIPS_LO16` immediate. If the retail binary happens to have `0` in both fields (e.g. referencing address `0x00000000` or an unlinked overlay binary where retail words are `0`), setting `_pending_lo[noff] = 0` matches the retail word instead of forcing a diff (`orig ^ 1` as done for GPREL16). Furthermore, `o.is_clean(f)` only checks `self.unresolved` and `self.unknown`, completely ignoring `self.placeholders`! Thus, if the raw words happen to match the binary's bytes, the function is reported as `match` despite a failed content check.
   - **Test:** Construct a test case (like `checks["anchor-content"]` in `self_test`) where the retail instruction at `off`/`noff` has immediate `0` (e.g., `lui $a0, 0; addiu $a0, $a0, 0`), and `_anchored` returns `(None, "content ...")`. Run relocation and compare: `o.is_clean(f)` is `True` and `ours == orig`, yielding a false `match`.

5. **Incorrect HI16/LO16 pairing across control-flow branches or multiple `%hi` to the same section**
   - **Location:** `tools/verify_decomp.py` (`Object._pair_by_offset`, `Object._section_lo_shared`) and `tools/harvest_relocs.py` (`harvest_function`).
   - **Mechanism:** In target mode, `_pair_by_offset` pairs each `R_MIPS_HI16` at `off` with the *first* `R_MIPS_LO16` at `noff > off` in the same function that has the same symbol index `si`. For section symbols (`STT_SECTION`, such as `.rodata` or `.sdata`), *all* references to that section in the function share the exact same symbol index `si`.
     - If GCC emits two `lui` instructions for `.rodata` before their respective `%lo` instructions (common when scheduling across basic blocks or loading two addresses into different registers before using them: `lui $t0, %hi(.rodata+0); lui $t1, %hi(.rodata+0x10000); addiu $t0, %lo(.rodata+0); addiu $t1, %lo(.rodata+0x10000)`), both HI16s at `off1` and `off2` have `noff = first_lo` (since `_pair_by_offset` does not track which LO16s are already claimed, or even if it did, they are paired in the wrong order). The second HI16 overwrites `self._pending_lo[first_lo]`, and the second LO16 falls through to `_section_lo_shared`, which pairs both LO16s with `max(his)` (`off2`). The first HI16 gets the wrong carry adjustments and the first LO16 gets the wrong addend.
   - **Test:** Assemble a function with interleaved `lui`/`addiu` to `.rodata+0x0` and `.rodata+0x8000` (where the second has a negative signed 16-bit lo requiring a carry into `%hi`). `_pair_by_offset` pairs both `lui` instructions with the first `addiu` (or pairs them by linear address rather than register/addend), corrupting the relocated `%hi` carry bit.

6. **`_func_bounds` / `_func_of` miscomputes function boundaries when `static` functions or non-zero-based functions exist**
   - **Location:** `tools/verify_decomp.py` (`Object._func_bounds`, `Object._func_of`).
   - **Mechanism:** `_func_bounds` builds boundaries from `{s["val"] for s in self.symbols if s["typ"] == STT_FUNC and s["shndx"] == self.text_idx}`. If a hand-written asm block or compiler output emits a local helper without `STT_FUNC` (`STT_NOTYPE`), or if a function has trailing literal pools/padding before the next `STT_FUNC`, `_func_of` merges them. More importantly, in `Object.__init__`, `self.funcs` only includes functions known in `self.syms` (`Symbols`), whereas `_func_bounds` uses ELF symbol table `STT_FUNC` entries; if they diverge, `_off_to_va` returns `None` for the second function while `_func_of` separates them (or vice versa).

7. **`harvest_relocs.py` and `port_check.py` silently drop multiple relocations at the same offset or miss HI16 differences when harvesting**
   - **Location:** `tools/harvest_relocs.py` (`masked_compare`, `harvest_function`).
   - **Mechanism:** In `harvest_function`, `R_MIPS_HI16` is never harvested on its own; it is only read when an `R_MIPS_LO16` looks backward for `his = [o2 for o2, t2, s2 in rel if s2 == si and t2 == R_MIPS_HI16 and f["val"] <= o2 < off]`.
     1. Just like Finding 5, if `si` is a section symbol (`STT_SECTION`), `max(his)` picks the most recent `R_MIPS_HI16` for that section, which is wrong whenever two registers hold different `%hi` values for the same section across interleaved instructions.
     2. If a compiler CSEs or hoists a `lui` *after* a loop body in layout (forward branch to loop header, backward branch to body), `o2 > off`, so `his` is empty and the relocation is silently skipped.
   - **Test:** In `harvest_relocs.py`, test a function with two interleaved `R_MIPS_HI16` / `R_MIPS_LO16` pairs against section symbol `.data` at offsets `+0x0` and `+0x10000`. `harvest_function` computes the wrong section base `(V - addend)` for the first LO16, creating a false section conflict in `summarize()`.

8. **Command injection / word-splitting in Docker `build_script` via `@cflags` annotations**
   - **Location:** `tools/verify_decomp.py` (`build_script`, `run_target`, `parse_annotations`).
   - **Mechanism:** `parse_annotations` extracts `@cflags` directly from C source comments (`r"@cflags\s+([^*\n]+)"`). `run_target` passes those tokens into `extra`, which is interpolated *unquoted* into the shell script `work/build.sh` inside `build_script`:
     `cc1, cc1_extra = "$LD " + STOCK_CC1, stock_cc1_flags` -> `f'  {cc1} -quiet ... {cc1_extra} "$i" ...'`.
     Any semicolon, backtick, `$()`, or redirection in a `/* @cflags ... */` comment executes arbitrary shell commands inside the container (which has `/work` mounted read-write on the host). Even benign flags with spaces or shell metacharacters (e.g., `-Dfoo="a b"`) break the shell command.
   - **Test:** Add `/* @cflags -O2 ; touch /work/pwned */` to a C file and run `verify_decomp.py --target ...`. After the run, `work/pwned` exists on the host filesystem.

9. **Tag collision between TU IDs (`/` vs `__`) overwrites object files and flags**
   - **Location:** `tools/verify_decomp.py` (`run_target`, line 1384: `tag = t["id"].replace("/", "__")`) and `tools/port_check.py` (`build`, line 101).
   - **Mechanism:** Both `main/foo__bar` and `main__foo/bar` map to `main__foo__bar`. More importantly, in `run_target`, warnings reconstruct the TU ID with `l.split()[1].replace("__", "/")` (line 1435), corrupting any TU ID that legitimately contained `__` in its filename.
   - **Test:** Name a TU `main/a__b` in `decomp-target.json` and trigger an `ASWARN`. The report's `warnings` list records `tu: "main/a/b"`, which does not match any TU ID in the manifest.

10. **Hardcoded `clang` host dependency without target triple during preprocessing**
    - **Location:** `tools/verify_decomp.py` (`run_target`, line 1385) and `tools/port_check.py` (`build`, line 102).
    - **Mechanism:** Preprocessing runs `["clang", "-E", "-P", "-DSKIP_ASM", ...]` on the *host* machine with no `-target` or `-nostdinc` flag.
      1. Fails immediately with `FileNotFoundError` on machines that have `gcc`/`cpp` installed instead of `clang` (and `subprocess.run` is not wrapped in `try/except FileNotFoundError`, crashing the verifier instead of reporting a tooling error in `doctor()`).
      2. Because no `-target` or `-nostdinc` is passed, host `clang` predefines host architecture macros (`__x86_64__`, `__aarch64__`, `__LP64__`, `__APPLE__`, `__linux__`) and searches host `/usr/include` if any `<...>` header is included. A TU checking `#ifdef __LP64__` or `sizeof(long)` in preprocessor conditionals will preprocess differently across x86_64/arm64/macOS/Linux hosts instead of matching 32-bit MIPS EE (`__mips__`, `_MIPS_SZLONG=32`).
    - **Test:** Put `#ifdef __x86_64__\n#error host macro leaked\n#endif` in a target TU and run `verify_decomp.py --target ...` on an x86_64 host: preprocessing fails even though the target is PS2 MIPS R5900.

11. **`ledger.py all` and `ledger.py check` ignore duplicate function names across TUs in the same unit**
    - **Location:** `tools/ledger.py` (`cmd_all`, line 168: `why = {m["func"]: m["kind"] ...}`).
    - **Mechanism:** `static` functions in different TUs of the same unit frequently share names (e.g., `Init`, `Update`, `cb`). In `cmd_all`, `tier` is keyed by `(f["name"], int(f["va"], 16), int(f["size"]))`, which is safe, *unless* two TUs in the manifest mistakenly define the same symbol at the same VA, in which case one passing and one failing still adds the tuple to `tier` and passes `cmd_all`. Meanwhile, `why` is keyed only by `m["func"]`, so a mismatch in TU B overwrites the failure reason for a same-named static function in TU A. Similarly, in `sibling_verdicts` (`ledger.py`, line 198), `by = {f["func"]: f for f in report.get("functions") or []}` and `mapping` in `port_check.py` (`load_map`) are keyed solely by function name `p[0]`, colliding whenever two TUs have a local/static function with the same name.
    - **Test:** Have two TUs in `main` both define `static void init(void)` at different addresses. Run `ledger.py sibling`: `by` and `mapping` overwrite the first `init` with the second, judging both ledger rows against the second function's verdict and address.
